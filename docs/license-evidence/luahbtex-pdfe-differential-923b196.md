# LuaHBTeX pdfe/pdfscanner differential evidence (`923b196`)

This record compares the internal, pre-WTPDF `pplib` baseline with the
Xpdf/WTPDF candidate for LuaHBTeX's public Lua PDF surface: `pdfe` and
`pdfscanner`. It covers API behavior on native code-generation builds only. It
does not approve visual output compatibility or clear an engine release.

## Compared behavior

The probe exercises, through the public Lua API only:

- `pdfe.open`, catalog/trailer/info access, and `pdfe.type` on every returned
  value;
- dictionary iteration order via indexed `pdfe.getfromdictionary`;
- string bytes and lexical form: literal and hex spellings, decoded and raw
  access, embedded NUL bytes;
- raw and decoded whole-stream reads plus chunked stream reads;
- `pdfscanner.scan` over both a string program and a stream, covering integer,
  real, boolean, name (with `#xx` escape), string, array, dictionary operands;
- a classic-xref document, an xref-stream/object-stream document, an RC4-128
  encrypted document (initial status, wrong password, user password), a
  300-level nested document, and a damaged-but-repairable document.

## Results

- Clean-input behavior (classic, xref/object stream, encrypted, deep) was
  byte-identical between baseline and candidate after removing the `damaged`
  key: the shared JSON serialization matched exactly.
- Baseline output: 2,642 bytes, SHA-256
  `72bbac30b435ec70ab833e5ecafc29a0627ed0842ea576386ae153fbe4a5ab15`.
- Candidate output: 2,663 bytes, SHA-256
  `880f34905d96d705dab09621e92d8ba65ff1c764197f957fdcb0beffa7b2e981`.

The single difference is the damaged fixture (its `startxref` offset is
blanked): `pplib` failed to open it (`opened=false`) while Xpdf reconstructs
the xref table and opens it with one page and seven objects. Classification:
**expected and approved** — Xpdf's documented damage recovery is a strict
superset of the baseline's behavior, no previously-supported input regressed,
and the repaired result is stable. This matches the WTPDF adapter contract that
differential fixtures must approve malformed-input recovery differences.

The candidate's full probe output is checked in as
`wasm-build/pdf-backend/fixtures/luahbtex-pdf-api.expected.json`, and
`scripts/build-luatex-fromsource.sh` re-runs the same probe against the native
code-generation build and requires byte equality before it exports WebAssembly
artifacts. The same build runs the repeat-image fixture
(`wasm-build/pdf-backend/fixtures/luahbtex-repeat-image.tex`) five times: it
opens the classic-xref and xref/object-stream fixtures twice each and ships
them out, covering image inclusion over both xref layouts and the
PdfDocument/WTPDF lifetime boundary.

## Memory release

Valgrind (`--leak-check=full`) ran against the candidate native binary in the
same environment:

- the full pdfe/pdfscanner probe — open/close, values, stream readers, failed
  and successful authentication, damaged input, and garbage-collected
  userdata — reported **0 bytes definitely or indirectly lost and 0 errors**;
- the repeat-image inclusion fixture reported 1,504 definitely-lost bytes in
  75 blocks, **byte-for-byte equal to the pplib baseline's total on the same
  fixture**. The records trace to upstream kpathsea path handling and the
  `PdfDocument` registry node that upstream intentionally retains at exit
  (`destroyPdfDocument` carries an upstream TODO); none trace to `wtpdf_*`
  frames. The WTPDF port introduces no new leak;
- the WTPDF smoke test additionally asserts a zero child-handle count after
  every success, failure, and locked-document path.

## Remaining scope

This evidence does not cover `graphicx`/`pdfpages`/TikZ package-level import
differentials against the baseline, post-open authentication through image
inclusion, malformed-input resource limits, memory-release verification,
text-position output comparison, browser/Node parity, or performance budgets.
It compares native binaries; the release gates bind the same sources to the
WebAssembly artifacts through the from-source Docker build.
